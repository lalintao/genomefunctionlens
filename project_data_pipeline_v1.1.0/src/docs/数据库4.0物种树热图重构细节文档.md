# 数据库 4.0 物种树与热图重构细节文档

本文档整理未来面向大规模基因组数据量时，物种树、基因组表、热图矩阵、购物车与下载流程所需的数据库和数据文件调整。目标数据规模以约 20 万条基因组/树叶子为参考。

本文档只描述数据库和数据产物侧需要配合的内容；前端状态管理和后端接口实现会另行拆分。但为了避免数据库字段脱离真实使用场景，本文先说明新系统的整体运行逻辑。

## 1. 核心结论

新的设计中，物种树高频交互主要在前端内存完成，后端主要负责基因组筛选、矩阵聚合、蛋白下载和数据包生成。

数据库不再为前端展开、折叠、搜索、条带分组等高频树操作建立大量查询索引；这些索引应进入前端 tree core 包或后端启动时的内存索引。

数据库需要重点保证三件事：

- 能稳定生成一份紧凑的前端 tree core。
- 能从原始树叶子节点快速定位到 genome，并用 `genome_id` 直接定位矩阵行。
- 能支持后端对 genome 质量字段、注释矩阵、蛋白下载的高效查询。

因此，`leaf_left / leaf_right`、`name_id`、`label` 不作为数据库核心必需字段。它们最多是运行时派生索引或前端压缩格式的一部分，不应强制落到主表里。

## 2. 新系统运行逻辑

### 2.1 数据集加载

用户选择 `species_tree + genome_database` 后，后端返回数据集元信息和 tree core 包路径。

tree core 包由数据库或构建流程生成，前端一次性加载整棵树的紧凑结构。即使未来有 20 万叶子，只要格式是数组/bitset，而不是大对象嵌套树，前端内存仍可接受。

前端加载后构建以下内存结构：

```text
node arrays:
  parent[]
  nodeIn[]
  nodeOut[]
  rank[]
  branchLength[]
  cumulativeBranchLength[]
  name / taxonName 引用

direct child index:
  childrenByParent
  或 childrenOffsets[] + childrenPool[]

state bitsets:
  aliveBitset
  expandedBitset
  cartAliveBitset

runtime indexes:
  terminalNodeIds[]
  rankIndexes[rank]
  rankIndexes[rank] fields:
    taxon_name
    taxon_name_norm
    node_id
```

这里要区分“真相结构”和“加速结构”：

- `parent[] + nodeIn[] + nodeOut[]` 足以恢复树结构和祖先/后代关系。
- 但只靠 DFS 区间不能直接 O(1) 取出“直接孩子”，因为子树区间里同时包含孩子、孙子和更深后代。
- 因此前端仍建议维护一份“直接孩子索引”。它可以是普通的 `childrenByParent`，也可以压成 `childrenOffsets[] + childrenPool[]`，这属于实现细节，不是数据库字段要求。
- `rankIndexes[rank]` 是前端高频索引，不是数据库高频查询索引。

### 2.2 物种树展开、折叠和全局展开 rank

前端不再每次向后端请求子树结构。

展开某个终端节点时：

1. 前端根据 `node_id` 找到该节点。
2. 根据 `nodeIn / nodeOut` 和直接孩子索引找到该节点下一级或目标 rank 的节点。
3. 更新 `expandedBitset`。
4. 重新计算 `terminalNodeIds[]`。
5. 根据新的 `terminalNodeIds[]` 请求热图聚合矩阵。

切换全局展开 rank 时：

1. 前端读取 `rankIndexes[target_rank]`。
2. 用 `nodeIn / nodeOut` 判断这些 rank 节点是否在当前可见/存活范围内。
3. 更新 `terminalNodeIds[]`。
4. 请求后端按新的终端节点顺序聚合热图。

数据库不需要为这些操作建 `rank + nodeIn` 的高频查询索引，因为这些操作发生在前端内存里。

### 2.3 条带展示

条带展示也在前端完成分组。

当用户选择条带 rank：

1. 前端从 `rankIndexes[strip_rank]` 取对应 rank 的命名节点。
2. 用 `nodeIn / nodeOut` 与当前终端节点判断归属关系。
3. 前端直接从该 rank 索引表中的 `taxon_name` 显示条带名称，不需要再向后端查询名称。

这意味着不再需要为每个 genome 在数据库中保存完整 taxon path 只是为了画条带。

但是当前下载 FASTA header 仍会使用 taxonomy 字段。因此 `taxonomy` 表是否删除，取决于下载 header 是否改为从树祖先节点动态生成 taxonomy path。见本文第 5 节。

### 2.4 genome 条件筛选

genome 明细不搬到前端。

筛选流程：

1. 前端把当前作用范围传给后端。默认范围可以是整棵树、当前可视树、购物车树，具体用 `terminal_node_ids`、选中子树列表或压缩 leaf bitset 表达。
2. 后端根据 `genome.leaf_node_id` 找到候选 genome。
3. 后端用 `genome` 表中的质量字段筛选，例如 `checkm2_completeness`、`checkm2_contamination`、`quality_score`、`contig`。
4. 后端返回不满足条件的 `leaf_node_id[]`，或返回满足条件的压缩 leaf bitset。
5. 前端更新 `aliveBitset` 或 `cartAliveBitset`。
6. 前端根据剩余叶子向上维护内部节点：没有存活孩子的内部节点也置为不可用。
7. 前端重建 `terminalNodeIds[]` 和渲染树。

这里数据库需要优化的是 `genome` 筛选字段和 `leaf_node_id -> genome_id` 映射，不是前端树展开索引。

### 2.5 热图聚合

前端不再把整棵树的所有叶子矩阵搬到浏览器后再聚合。

请求热图时，前端发送：

```json
{
  "terminal_node_ids": [123, 456, 789],
  "annotation_columns": ["K00001", "K00002"],
  "scope": {
    "mode": "all" 
  }
}
```

如果当前树已经经过删除/筛选，`scope` 需要表达当前存活叶子集合：

```json
{
  "terminal_node_ids": [123, 456, 789],
  "annotation_columns": ["K00001", "K00002"],
  "scope": {
    "mode": "alive_leaf_bitmap",
    "encoding": "compressed",
    "data": "..."
  }
}
```

后端处理：

1. 对每个 `terminal_node_id`，通过后端内存索引展开到底层 `leaf_node_id[]`。
2. 如果请求带有 `alive_leaf_bitmap`，则与终端节点的叶子集合求交集。
3. 通过 `genome.leaf_node_id -> genome_id` 找到矩阵行；新系统约定 `genome_id` 就是矩阵行号。
4. 从 Parquet / 列式矩阵读取请求的注释列。
5. 对每个终端节点聚合 count、ratio、species_hit_count 等值。
6. 按前端传入的 `terminal_node_ids` 顺序返回矩阵。

返回示例：

```json
{
  "row_node_ids": [123, 456, 789],
  "columns": ["K00001", "K00002"],
  "matrix": [
    [10, 3],
    [0, 7],
    [5, 1]
  ],
  "row_leaf_counts": [38, 12, 9]
}
```

这样前端热图行顺序由 `terminal_node_ids` 保证，不再依赖旧的 `leaf_order` 大数组对齐。

### 2.6 购物车

购物车不再支持“所有分支记录行”视图，只保留“操作批次”视图。

前端维护：

```text
cartAliveBitset
cartBatches[]
undoStack 最近 9 次操作
```

加入购物车时：

1. 前端把某个可视终端节点或一组节点的子树叶子加入 `cartAliveBitset`。
2. 同时做 ancestor closure，确保多个离散子树组合后仍然能画成完整树。
3. 记录一条 batch，包括来源、操作时间、选中祖先、展开 rank、加入的节点范围摘要。

数据库不需要为每个用户保存购物车树状态。

下载时：

1. 前端把购物车中的终端节点或压缩 leaf scope 发给后端。
2. 后端解析为 genome_id 集合。
3. 根据注释列查 `protein_annotation -> protein`。
4. 生成 FASTA 包。

## 3. 数据库表结构调整

以下为目标结构。若未来每棵物种树分表维护，则表名可以带树名后缀，例如 `tree_node_ar53_r226`。如果继续一个 SQLite 支持多棵树，则所有树相关表必须保留 `species_tree` 字段并进入联合索引。

本文默认采用用户当前倾向：不同物种树分表或分数据包维护，所以核心树表不强制保留 `species_tree`。

### 3.1 `tree_node`

用途：保存原始二叉树的结构和渲染所需数值，不保存冗余显示名。

目标字段：

```text
node_id INTEGER PRIMARY KEY
parent_id INTEGER NULL
node_in INTEGER NOT NULL
node_out INTEGER NOT NULL
rank TEXT NULL
is_leaf INTEGER NOT NULL
branch_length REAL NULL
cumulative_branch_length REAL NULL
```

字段说明：

- `node_id`：稳定节点 id，必须与前端 tree core 中的数组下标或 id 映射一致。
- `parent_id`：父节点 id；根节点为 null。
- `node_in / node_out`：全节点 DFS 区间，用于判断祖先/后代关系和子树包含关系。
- `rank`：有 taxon 名字的内部节点填 taxonomic rank，例如 `family`、`genus`；无名内部节点为 null。原始叶子节点不要简单等同于 `species`，当前项目中叶子更接近 accession/genome leaf。
- `is_leaf`：原始物种树叶子，不是前端当前可视终端节点。
- `branch_length`：父节点到当前节点的分支长度。
- `cumulative_branch_length`：根节点到当前节点的累积分支长度，用于矩形树和环形树布局。

建议删除或不再新增：

- 删除旧 `left_index / right_index` 的数据库核心语义。旧字段当前实际是叶子顺序区间，不是全节点 DFS 区间，容易与 `node_in / node_out` 混淆。
- 不新增 `leaf_left / leaf_right` 到数据库核心表。若后端需要，可启动时由 `node_in / node_out + leafIndex` 派生为内存索引。
- 不保留 `label` 作为核心字段。命名 taxon 的名字进入 `tree_named_taxon_index`；叶子节点显示名若需要，由 species rank 索引或前端 tree core 提供。
- 不保留 `leaf_count` 作为核心字段。当前筛选会动态改变叶子数，聚合时由后端或前端按当前 scope 计算。
- 不新增 `name_id`。字符串去重可以放在前端 tree core 的 `names[]`，不是数据库主表必需字段。

必要索引：

```sql
CREATE UNIQUE INDEX idx_tree_node_id ON tree_node(node_id);
CREATE INDEX idx_tree_node_parent ON tree_node(parent_id, node_id);
CREATE INDEX idx_tree_node_dfs ON tree_node(node_in, node_out);
```

说明：

- `idx_tree_node_id` 用于构建 tree core 和直接节点查找。
- `idx_tree_node_parent` 用于构建 children index。
- `idx_tree_node_dfs` 主要用于构建/校验和偶发后端范围查询，不是前端高频操作索引。

### 3.2 `tree_named_taxon_index`

用途：保存所有有 taxon 名字的节点。数据库中可以是一张表；前端使用时必须拆成每个 rank 的独立索引。

目标字段：

```text
rank TEXT NOT NULL
taxon_name TEXT NOT NULL
taxon_name_norm TEXT NOT NULL
node_id INTEGER NOT NULL
```

字段说明：

- `rank`：例如 `domain`、`phylum`、`class`、`order`、`family`、`genus`、`species`。
- `taxon_name`：原始展示名。
- `taxon_name_norm`：标准化搜索名，例如小写、去首尾空格、统一前缀处理。
- `node_id`：对应 `tree_node.node_id`。

必要索引：

```sql
CREATE INDEX idx_tree_named_taxon_lookup
ON tree_named_taxon_index(rank, taxon_name_norm, node_id);

CREATE INDEX idx_tree_named_taxon_rank_node
ON tree_named_taxon_index(rank, node_id);
```

使用场景：

- 构建前端每个 rank 一张索引表，字段为 `taxon_name`、`taxon_name_norm`、`node_id`。
- 支持后端直接 taxon 定位接口，如果后端未来仍提供按 rank/name 查 node_id。
- 生成条带和搜索索引。

注意：这张表不是为了每次前端搜索都查数据库。前端加载 tree core 后，应把它拆成内存索引。

### 3.3 `genome`

用途：保存 genome 实体、后端筛选字段、物种树叶子映射，并承担矩阵行对齐契约。

建议目标字段：

```text
genome_id INTEGER PRIMARY KEY
leaf_node_id INTEGER NOT NULL
genome_database TEXT NULL
genome_accession TEXT NOT NULL
genome_name TEXT NULL
checkm2_completeness REAL NULL
checkm2_contamination REAL NULL
quality_score REAL NULL
contig INTEGER NULL
species_genome_count INTEGER NULL
if_refseq INTEGER NULL
source TEXT NULL
source_version TEXT NULL
protein_key_start INTEGER NULL
protein_key_end_exclusive INTEGER NULL
```

核心约定：

- `genome_id` 必须是 0-based、连续、稳定、无空洞的 dense id。
- 所有 genome-annotation 矩阵行顺序必须严格等于 `genome` 表按 `genome_id ASC` 排序。
- 因此 `genome_id` 同时是 genome 主键和矩阵行定位键，不再单独保存 `matrix_row_index`。
- `leaf_node_id` 对应物种树中 species rank 的叶子节点。新系统约定 species rank 节点就是原始树叶子，且与 genome 一一对应。

建议从 `genome` 主表移走：

- `species_tree`：如果树分表/分包维护，则不需要在每条 genome 上重复。
- `tree_file`：属于数据集 registry，不属于 genome 实体。
- `leaf_label`：新系统不再需要；树叶子显示名由 `tree_named_taxon_index` 或前端 tree core 提供。
- `leaf_order_index`：新系统不再需要；矩阵行号由 `genome_id` 承担。
- `matrix_row_index`：不再新增；与 `genome_id` 语义合并。
- `taxonomy_id`：是否保留取决于下载 header 是否继续依赖 `taxonomy` 表。当前后端下载仍依赖 taxonomy，因此迁移初期可以保留，最终目标可以移除。
- `is_cultured`：未来纯培养筛选废弃后可移除；如果还要兼容旧界面，可暂时保留。

必要索引：

```sql
CREATE UNIQUE INDEX idx_genome_id
ON genome(genome_id);

CREATE UNIQUE INDEX idx_genome_leaf_node
ON genome(leaf_node_id);

CREATE INDEX idx_genome_accession
ON genome(genome_accession);

CREATE INDEX idx_genome_quality
ON genome(genome_database, checkm2_completeness, checkm2_contamination, quality_score);
```

如果 `if_refseq` 仍保留筛选：

```sql
CREATE INDEX idx_genome_refseq
ON genome(genome_database, if_refseq);
```

使用场景：

- genome 条件筛选。
- 通过 `leaf_node_id` 将树叶子映射到 genome。
- 通过 `genome_id` 直接定位矩阵行。
- 下载代表 genome 排序。
- 数据审计和 accession 搜索。

### 3.4 `taxonomy`

当前后端下载逻辑会 join `taxonomy` 表生成 FASTA header 中的 domain/phylum/class/order/family/genus/species，因此现在不能直接删除。

未来有两种选择：

方案 A：保留 `taxonomy` 表。

优点：下载 header 简单，兼容当前代码。缺点：与树上的命名 taxon 存在一定冗余。

方案 B：删除 `taxonomy` 表，下载 header 从树祖先路径生成。

要求：

- `tree_named_taxon_index` 必须覆盖所有需要展示/下载的 rank。
- 后端内存 tree index 能从 `leaf_node_id` 向上找到各 rank 祖先。
- 下载服务改为从树祖先路径组装 header。

建议：第一阶段保留 `taxonomy` 表，等下载服务改造完成后再删除。

### 3.5 `matrix_file`

用途：定位注释矩阵文件。

当前可保留字段：

```text
id
genome_database
annotation_type
matrix_path
matrix_format
```

建议移出或废弃：

- `tree_file`
- `tree_file_path`
- `leaf_order_path`
- `leaf_index_path`
- `leaf_accession_map_path`
- `metadata_path`
- `tree_data_path`

这些字段应迁移到数据集 registry / tree package registry，而不是每个 annotation matrix 重复保存。

必要索引：

```sql
CREATE INDEX idx_matrix_file_lookup
ON matrix_file(genome_database, annotation_type);
```

如果一个 SQLite 内仍保存多棵树：

```sql
CREATE INDEX idx_matrix_file_lookup
ON matrix_file(species_tree, genome_database, annotation_type);
```

### 3.6 `tree_dataset` 或改造 `species_tree_database_map`

当前 `species_tree_database_map` 负责告诉后端 tree 文件、tree_data、leaf_order、metadata 在哪里。新系统中建议改造成更明确的数据集 registry。

目标表名可以继续叫 `species_tree_database_map`，也可以新建 `tree_dataset`。

建议字段：

```text
species_tree TEXT NOT NULL
genome_database TEXT NOT NULL
tree_core_path TEXT NOT NULL
tree_newick_path TEXT NULL
matrix_row_count INTEGER NULL
leaf_count INTEGER NULL
node_count INTEGER NULL
source_version TEXT NULL
created_at TEXT NULL
```

必要索引：

```sql
CREATE UNIQUE INDEX idx_tree_dataset_lookup
ON tree_dataset(species_tree, genome_database);
```

说明：

- `tree_core_path` 指向新的前端 tree core 包。
- `tree_newick_path` 只用于导出、调试或兼容旧展示，不再作为主运行数据。
- 旧的 `leaf_order_path`、`metadata_path`、`tree_data_path` 在新架构下不再是运行期必需字段。

### 3.7 注释字典表

注释字典建议从当前统一 `annotation` 表，调整为按注释类型拆分的 4 类字典表。这样每类注释可以拥有稳定的本地整数 id、独立排序规则和清晰字段，不需要所有类型挤在同一张宽泛表里。

目标表：

```text
cog_annotation
- cog_id INTEGER PRIMARY KEY
- cog_code TEXT NOT NULL
- short_name TEXT NULL
- full_name TEXT NULL
- sort_order INTEGER NOT NULL

pfam_annotation
- pfam_id INTEGER PRIMARY KEY
- pfam_code TEXT NOT NULL
- short_name TEXT NULL
- full_name TEXT NULL
- sort_order INTEGER NOT NULL

kegg_annotation
- kegg_id INTEGER PRIMARY KEY
- ko_code TEXT NOT NULL
- short_name TEXT NULL
- full_name TEXT NULL
- sort_order INTEGER NOT NULL

module_annotation
- module_id INTEGER PRIMARY KEY
- module_code TEXT NOT NULL
- full_name TEXT NULL
- sort_order INTEGER NOT NULL
- kegg_url TEXT NULL
```

排序规则：

- `COG0205`、`K00001`、`M00001` 等编号中的数字可以在构建数据库时解析为 `sort_order`。
- `PF00047.15` 建议按主体号和版本号解析，至少保证 `sort_order` 稳定。
- SQLite 不应依赖物理插入顺序；所有查询、矩阵列构建和导出顺序都应显式使用 `sort_order`。
- 注释分布矩阵的列顺序必须与对应注释字典表的 `sort_order` 一致。

必要索引：

```sql
CREATE UNIQUE INDEX idx_cog_annotation_code ON cog_annotation(cog_code);
CREATE UNIQUE INDEX idx_pfam_annotation_code ON pfam_annotation(pfam_code);
CREATE UNIQUE INDEX idx_kegg_annotation_code ON kegg_annotation(ko_code);
CREATE UNIQUE INDEX idx_module_annotation_code ON module_annotation(module_code);
CREATE INDEX idx_cog_annotation_sort ON cog_annotation(sort_order);
CREATE INDEX idx_pfam_annotation_sort ON pfam_annotation(sort_order);
CREATE INDEX idx_kegg_annotation_sort ON kegg_annotation(sort_order);
CREATE INDEX idx_module_annotation_sort ON module_annotation(sort_order);
```

如果后端仍需要统一搜索接口，可以在后端运行时合并这 4 张表，或增加一个只读 view，但运行期核心字典建议按类型拆开。

### 3.8 Module 相关表

未来 Module 的目标功能收敛为：

- 根据 `module_code` 搜索和显示 module 全名。
- 展开该 module 包含的 KO list。
- 根据 module completeness 矩阵展示完整度。
- 根据 module 编号跳转 KEGG 官方链接。

因此，Module 不再需要完整 IR、step graph、AST graph 等复杂表作为运行期必需数据。

建议保留：

```text
module_annotation
module_kegg_member
module_completeness_file
```

新增关系表：

```text
module_kegg_member
- module_id INTEGER NOT NULL
- kegg_id INTEGER NOT NULL
- member_order INTEGER NOT NULL
```

说明：

- `module_kegg_member` 用于表达 module 包含哪些 KO，不建议把 KO list 作为 JSON 或逗号字符串塞进 `module_annotation`。
- `member_order` 用于稳定展开顺序，也用于 module detail 热图列顺序。
- `module_annotation.kegg_url` 可选；如果不存，也可以由 `https://www.kegg.jp/entry/{module_code}` 动态拼接。

必要索引：

```sql
CREATE INDEX idx_module_kegg_member_module
ON module_kegg_member(module_id, member_order, kegg_id);

CREATE INDEX idx_module_kegg_member_kegg
ON module_kegg_member(kegg_id, module_id);

CREATE INDEX idx_module_completeness_file_lookup
ON module_completeness_file(species_tree, genome_database);
```

可删除或不进入运行期必需库：

```text
kegg_module_step
kegg_module_edge
kegg_module_completeness_block
kegg_module_ref_expansion
kegg_module_ir_node
kegg_module_ir_edge
```

这些表只在需要 module step 级可视化、逻辑表达式解释、IR/graph 展示时才有意义。若产品目标只是展开 KO list、展示完整度和跳转官方链接，则不建议保留为运行期必需表。

### 3.9 `protein` 和 `protein_annotation`

蛋白下载功能仍需要蛋白级数据，但不再建议单独保留 `protein_sequence` 做序列去重。序列正文可以直接并入 `protein` 表，以减少下载时 join 链路。

目标结构：

```text
protein
- protein_key INTEGER PRIMARY KEY
- genome_id INTEGER NOT NULL
- protein_id TEXT NOT NULL
- protein_name TEXT NULL
- sequence TEXT NOT NULL
- sequence_length INTEGER NULL

protein_annotation
- annotation_hit_id INTEGER PRIMARY KEY
- annotation_type TEXT NOT NULL
- annotation_id INTEGER NOT NULL
- genome_id INTEGER NOT NULL
- protein_key INTEGER NOT NULL
```

说明：

- `protein_annotation` 仍然需要保留，因为按注释下载蛋白时，最有效入口是 `annotation -> protein hits`，不是先从 genome 扫全部蛋白。
- `genome_id` 在 `protein_annotation` 中是有意冗余字段，用于避免下载时反复通过 `protein` join 才能过滤 genome 范围。
- `protein_sequence` 不再作为目标运行期表；序列去重主要节省存储，不是下载查询加速。当前目标更重视下载链路清晰和少 join。

建议给 `genome` 增加蛋白物理区间字段：

```text
genome.protein_key_start
genome.protein_key_end_exclusive
```

构建约束：

- 同一 genome 的 protein 在 `protein` 表中连续存放。
- `protein_key_start <= protein_key < protein_key_end_exclusive` 表示该 genome 的蛋白区间。
- 该区间适合快速获取某 genome 的全部蛋白，或作为下载辅助优化；按注释下载时仍以 `protein_annotation` 为主入口。

必要索引：

```sql
CREATE UNIQUE INDEX idx_protein_key
ON protein(protein_key);

CREATE INDEX idx_protein_genome_range
ON protein(genome_id, protein_key);

CREATE INDEX idx_download_protein_annotation_lookup
ON protein_annotation(annotation_type, annotation_id, genome_id, protein_key);

CREATE INDEX idx_protein_annotation_genome
ON protein_annotation(genome_id, annotation_type, annotation_id);
```

这些索引对应下载和预览，不属于前端树高频操作。

#### 3.9.1 下载查询链路

目标下载链路采用“注释优先，genome scope 过滤”的方向。

前端请求提供：

```text
leaf/node scope
annotation_type
annotation_id 或 annotation_code
```

后端处理顺序：

1. 将前端 scope 解析为 `genome_id` 范围。
2. 将 `annotation_code` 解析为对应类型下的整数 `annotation_id`。
3. 以 `protein_annotation(annotation_type, annotation_id, genome_id, protein_key)` 为主入口查命中蛋白。
4. 用命中的 `protein_key` 回表查询 `protein.protein_id`、`protein_name`、`sequence`、`sequence_length`。
5. 按请求的 header 字段生成 FASTA。

小范围下载时，可以直接使用：

```sql
SELECT p.protein_key, p.protein_id, p.protein_name, p.sequence, p.sequence_length, pa.genome_id
FROM protein_annotation AS pa
JOIN protein AS p
  ON p.protein_key = pa.protein_key
WHERE pa.annotation_type = :annotation_type
  AND pa.annotation_id = :annotation_id
  AND pa.genome_id IN :genome_ids
ORDER BY pa.genome_id ASC, pa.protein_key ASC;
```

大范围下载时，不建议传入巨大的 `IN (...)` 列表。后端应为本次请求构建临时 scope 表或内存 bitset，然后与 `protein_annotation` 求交集：

```sql
SELECT p.protein_key, p.protein_id, p.protein_name, p.sequence, p.sequence_length, pa.genome_id
FROM protein_annotation AS pa
JOIN request_genome_scope AS s
  ON s.genome_id = pa.genome_id
JOIN protein AS p
  ON p.protein_key = pa.protein_key
WHERE pa.annotation_type = :annotation_type
  AND pa.annotation_id = :annotation_id
ORDER BY pa.genome_id ASC, pa.protein_key ASC;
```

说明：

- `protein_annotation` 是按注释下载的核心倒排表，不建议删除。
- `genome.protein_key_start / protein_key_end_exclusive` 用于按 genome 快速取全部蛋白，或作为连续性校验和辅助优化。
- 按注释下载时不应从 genome 蛋白区间逐个扫描再筛注释，因为这会让成本接近候选 genome 的总蛋白数，而不是实际命中数。

### 3.10 `taxon_representative`

`taxon_representative` 不作为新系统运行期必需表。

原因：

- 当前主下载逻辑没有依赖它。
- 代表 genome 可以根据当前 branch 的候选 genomes、`quality_score`、`contig`、`species_genome_count` 等字段动态计算。
- 预计算代表 genome 容易和用户筛选后的动态范围不一致。

因此：

- 运行期数据库可以删除 `taxon_representative`。
- 如需审计或构建报告，可保留在构建产物归档中，不进入线上部署包。

## 4. 数据库中不建议保留的字段

### 4.1 `tree_node.left_index / right_index`

当前数据库中的 `left_index / right_index` 实际更接近 leaf-order 区间，而不是全节点 DFS 区间。未来应避免继续用这个名字。

替代：

- 全节点 DFS 区间：`node_in / node_out`。
- 后端 node 到 leaf 的加速映射：启动时派生，不作为数据库核心字段。
- 矩阵行定位：`genome_id`，前提是所有矩阵严格按 `genome_id ASC` 构建行顺序。

### 4.2 `tree_node.label`

不建议保留为核心字段。

替代：

- 命名 taxon 节点名称：`tree_named_taxon_index.taxon_name`。
- 原始叶子名称：由 species rank 的 `tree_named_taxon_index.taxon_name` 或前端 tree core 提供。
- 前端压缩显示名：tree core 的 `names[]` 或等价结构。

### 4.3 `name_id`

不建议进入数据库核心表。

`name_id` 的价值是减少前端传输包中的重复字符串，因此它属于 tree core 文件格式优化，不属于数据库主表必需字段。

### 4.4 `genome.leaf_order_index`

建议删除，不再迁移为新字段。

新系统约定：

```text
matrix row index = genome_id
```

前提是 `genome_id` 必须是 0-based、连续、稳定、无空洞的 dense id，所有矩阵文件都严格按 `genome_id ASC` 构建行顺序。

### 4.5 `genome.leaf_label`

建议删除。

原因：新系统不再用 leaf label 做树、矩阵或下载匹配。树叶子通过 `leaf_node_id` 对齐 genome，矩阵行通过 `genome_id` 对齐。

### 4.6 `genome.species_tree / genome.tree_file`

如果采用一树一表或一数据包一树，这两个字段是冗余的。

如果继续一个 SQLite 支持多棵树，则可以暂时保留 `species_tree`，但需要承认这是多树部署策略带来的字段，而不是 genome 本身属性。

## 6. 后端运行时可预计算的数据

以下内容建议在后端启动时从 SQLite 和 tree core 构建到内存，或作为 sidecar 文件生成，但不建议作为数据库主表强制保存。

### 6.1 `nodeToLeafIds` 或 `nodeToLeafRange`

用途：热图聚合和下载时把 `terminal_node_id` 展开成底层叶子。

生成方式：

- 根据 `tree_node.node_in / node_out`。
- 从 `genome.leaf_node_id` 取所有原始叶子。
- 如果矩阵行顺序与 DFS 叶子顺序一致，可以压缩为 range。
- 如果不连续，则保存 leaf id 数组或 offset/pool 结构。

不落库原因：

- 它是 `tree_node + genome.leaf_node_id` 的派生结果。
- 筛选后叶子动态变化，最终仍要与请求 scope 求交集。

### 6.2 `leafNodeToGenomeId`

用途：genome 筛选、热图聚合和下载。

来源：

```text
genome.leaf_node_id -> genome.genome_id
```

可以直接从 `genome` 加载成数组。由于新系统约定 `genome_id` 就是矩阵行号，热图聚合不再需要单独的 `matrix_row_index`。

### 6.3 `parent / children / rank indexes`

用途：

- 后端校验请求 node 是否存在。
- 后端从 leaf 向上构造 taxonomy path。
- 后端可选支持 taxon 定位。

注意：前端也会构建一份自己的同类索引，这是合理的。前端索引用于交互；后端索引用于聚合、下载和校验。

### 6.4 `request_genome_scope`

用途：大范围蛋白下载时表达本次请求的 genome 范围。

实现方式：

- 小范围请求可以直接使用 `genome_id IN (...)`。
- 大范围请求应在后端运行时构建临时表、临时内存集合或 bitset。
- 该结构只属于单次请求，不作为永久数据库表保存。

示例临时表：

```text
request_genome_scope
- genome_id INTEGER PRIMARY KEY
```

使用场景：

- 与 `protein_annotation` join，避免超长 `IN` 列表。
- 将下载成本控制在“注释命中 protein 数量”和“本次 genome scope 交集”上。

## 7. 迁移顺序建议

### 阶段 1：增加新表，不破坏旧接口

新增：

```text
tree_node.node_in
tree_node.node_out
tree_named_taxon_index
genome.leaf_node_id
genome.protein_key_start
genome.protein_key_end_exclusive
tree_core 文件
```

保留旧：

```text
left_index / right_index
leaf_order.json
metadata.tsv
tree.json
index.json
genome.leaf_label
genome.leaf_order_index
taxonomy
```

目的：让数据库侧先产出新结构，前后端可以并行开发，不影响当前系统运行。

### 阶段 2：后端切换到 node_id 聚合接口

后端新增热图聚合接口：

```text
terminal_node_ids + annotation_columns + scope -> aggregated matrix
```

后端新增 genome 筛选接口：

```text
scope + genome filters -> removed_leaf_node_ids 或 alive_leaf_bitmap
```

此阶段矩阵仍可用现有 Parquet，但后端不再返回整棵树的 leaf-level matrix 给前端。

### 阶段 3：前端切换到 tree core 和 bitset 状态

前端改为：

- 加载紧凑 tree core。
- 自建 rank/taxon/children 索引。
- 本地维护 `aliveBitset`、`expandedBitset`、`terminalNodeIds`。
- 热图每次向后端请求聚合结果。

此阶段旧 `tree_data`、`tree_index`、`leaf_order` 可以仅作为兼容回退。

### 阶段 4：瘦身数据库和文件

确认新接口稳定后删除或停止部署：

```text
tree_node.left_index
tree_node.right_index
tree_node.label
tree_node.leaf_count
genome.leaf_label
genome.leaf_order_index
species_tree_database_map 旧路径字段
processed/tree_index/**
processed/species_tree/tree.json
processed/species_tree/index.json
processed/tables/*.parquet
processed/reports/*
```

如果下载 header 已从树祖先路径生成，则可以再考虑删除 `taxonomy` 表。

## 8. 数据一致性要求

### 8.1 节点 id 稳定

`tree_node.node_id` 必须在同一数据包版本内稳定，并与 tree core、`tree_named_taxon_index`、`genome.leaf_node_id` 一致。

### 8.2 DFS 区间规则

必须满足：

```text
node_in[u] <= node_in[v] <= node_out[u]
```

当且仅当 `v` 是 `u` 的后代时成立。

`node_in / node_out` 是全节点 DFS，不是叶子顺序。

### 8.3 矩阵行顺序

所有 annotation matrix 和 module completeness matrix 的行顺序必须与 `genome_id` 一致。

硬约束：

```text
genome_id 必须是 0-based、连续、稳定、无空洞的 dense id
matrix row i <-> genome.genome_id = i
所有矩阵文件必须按 genome_id ASC 构建行顺序
```

如果未来重建数据库导致 `genome_id` 改变，则所有 genome-annotation 矩阵和 module completeness 矩阵必须同步重建。

### 8.4 原始叶子与 species rank

新系统约定 species rank 节点就是原始树叶子，且与 `genome` 表中的记录一一对应。

因此：

- `tree_named_taxon_index(rank='species')` 中的 `node_id` 应与 `genome.leaf_node_id` 对齐。
- `genome.leaf_node_id` 必须唯一。
- 如果未来一个 species 节点对应多个 genome，这个约定需要重新审查。

### 8.5 多个离散子树要做 ancestor closure

购物车或筛选后如果保留多个离散子树，前端渲染前必须把这些子树到共同祖先路径上的内部节点也纳入可见集合。

数据库不需要存这个用户态结果。

## 9. 推荐的目标最小 schema

如果只列新树/热图架构必需表，目标最小集合是：

```text
tree_node
tree_named_taxon_index
genome
matrix_file
cog_annotation
pfam_annotation
kegg_annotation
module_annotation
module_kegg_member
protein
protein_annotation
module_completeness_file          -- 如果启用 module
tree_dataset / species_tree_database_map
```

兼容保留表：

```text
taxonomy

annotation_meta_cog          -- 仅兼容旧 AnnotationService
annotation_meta_kegg         -- 仅兼容旧 AnnotationService
annotation_meta_pfam         -- 仅兼容旧 AnnotationService
```

其中：

- `taxonomy`：当前下载 header 仍用，第一阶段保留。
- `annotation_meta_*`：当前 `AnnotationService` 兼容使用，长期可并入 `annotation`。
- `taxon_representative`：新系统运行期不需要，可放入构建归档或删除。

## 10. 需要数据库侧优先完成的任务清单

1. 为每棵树生成真正的全节点 DFS 编号：`node_in / node_out`。
2. 生成 `tree_named_taxon_index`，只包含有 taxon 名字的节点。
3. 在 `genome` 中生成 `leaf_node_id`，明确 species rank 叶子节点与 genome 一一对应。
4. 将 `genome_id` 生成为 0-based、连续、稳定、无空洞的 dense id，并按 `genome_id ASC` 构建所有矩阵行。
5. 删除目标 schema 中的 `tree_leaf`、`leaf_label`、`leaf_order_index`、`matrix_row_index`。
6. 生成紧凑 tree core 文件，供前端一次性加载。
7. 确认所有矩阵文件行顺序与 `genome_id` 完全一致。
8. 给 genome 筛选字段和 protein download 路径补齐必要索引。
9. 生成 `cog_annotation`、`pfam_annotation`、`kegg_annotation`、`module_annotation` 和 `module_kegg_member`，并保证字典顺序与矩阵列顺序一致。
10. 将蛋白序列正文并入 `protein`，不再单独保留 `protein_sequence` 作为目标运行期表。
11. 把旧 `species_tree_database_map` 的路径字段改造成 `tree_dataset` 风格 registry。
12. 给部署包做瘦身：运行期只带 SQLite、tree core、矩阵、module completeness、manifest。
13. 保留旧字段和旧文件一个版本作为兼容期，等前后端切换完成后再删除。
