# 数据库 4.0 构建逻辑与输入规范

本文说明 4.0 构建流程如何消费原始输入、如何组织成运行期数据包，以及未来接入新树和新数据库时该怎么做。

当前工作区约定：

- 原始输入统一放在 `row_data/`
- 运行期产物统一写到 `project_data/`
- 构建代码和构建文档统一放在 `src/`
- 临时构建物和 smoke 数据统一放在 `temporary_file/`

## 1. 总体思路

4.0 的构建目标是直接产出后端运行期最小集：

- SQLite 主库
- `tree_core.bin`
- annotation 热图矩阵 parquet
- module 完整度矩阵 parquet
- manifest

也就是说：

- 构建期的审计表、中间 TSV、兼容 SQLite、旧树索引文件，都不再进入 `project_data`
- `project_data` 默认只存后端实际读取的内容

当前实现还额外做了这些性能与稳定性处理：

- `.faa` 由主进程顺序读取；`--workers` 不控制 FASTA 并发
- annotation TSV 支持按 chunk 流式读取
- 单进程模式直接把 annotation 写入 `annotation_hits.sqlite`，不再产生 annotation Parquet 中继
- 多进程模式按文件分片并发解析，worker 先写 Parquet chunk，再由主流程汇总
- 默认 `--workers 1`，因为每个额外 annotation worker 都会复制一份蛋白查找表
- 最终 SQLite 使用构建期 PRAGMA、批量事务和延迟索引创建

## 2. 原始输入格式

### 2.1 物种树映射

文件：

`row_data/GTDB_speciesTree/speciesTree_genomesDatabase_mapping.txt`

格式：

```text
{tree_dir} : {genome_database_dir}
```

示例：

```text
GTDB226 : archaea226
```

含义：

- 左侧写的是 `GTDB_speciesTree/` 下的物种树目录名，不再直接写树文件名
- 右侧写的是 `protein_anno/` 下的 genome database 目录名
- 一棵树目录绑定一个 genome database 目录
- 4.0 按这个映射生成单树单数据库数据包

### 2.2 物种树文件

目录：

`row_data/GTDB_speciesTree/{tree_dir}/`

目录内要求：

- 固定放一个 `taxonomy.tsv`
- 固定放一个以 `.tre` 结尾的树文件
- 当前实现只接受目录内唯一的 `.tre` 树文件，不再兼容旧的 `.tree/.nwk/.newick` 输入

要求：

- Newick 格式
- 叶子标签需要能和 taxonomy 文件、`genome_leafLabel_mapping.tsv` 对上
- `species_tree` 标识默认使用 `{tree_dir}` 目录名，而不是树文件 stem

### 2.3 taxonomy 文件

文件：

`row_data/GTDB_speciesTree/{tree_dir}/taxonomy.tsv`

最少字段：

- `accession`
- `gtdb_taxonomy`

当前还会读取以下字段：

- `if_refseq`
- `checkm2_completeness`
- `checkm2_contamination`
- `quality_score`
- `contig`
- `species_genome_count`

注意：

- `is_cultured` 已不再进入 4.0 运行期

### 2.4 genome 与树叶映射

文件：

`row_data/protein_anno/{genome_database}/genome_leafLabel_mapping.tsv`

必需字段：

- `genome_name`
- `leaf_label`

要求：

- `leaf_label` 必须唯一
- `genome_name` 必须唯一
- 每个树叶都必须能映射到一个 genome

### 2.5 蛋白 FASTA

目录：

`row_data/protein_anno/{genome_database}/protein/*.faa`

要求：

- 每个文件代表一个 genome
- 文件名 stem 用于推断 `genome_accession`
- FASTA 记录 id 作为 `protein_id`

### 2.6 注释命中表

目录：

`row_data/protein_anno/{genome_database}/annotation/*.tsv`

当前支持：

- `cog.tsv`
- `kegg.tsv`
- `pfam.tsv`

格式：

- 第 1 列：`protein_id`
- 第 2 列：annotation 值
- 多值命中使用 `;;` 分隔

### 2.7 注释名字表

文件：

- `row_data/protein_anno/cog_annotation_names.tsv`
- `row_data/protein_anno/kegg_annotation_names.tsv`
- `row_data/protein_anno/pfam_annotation_names.tsv`

最少字段：

- `accession`

其他字段会作为字典补充信息带入 SQLite。

### 2.8 KEGG Module 原始文件

目录：

`row_data/module_source/kegg_module/raw/`

需要：

- `info_module.txt`
- `list_module.tsv`
- `link_ko_module.tsv`
- `entries/M*.txt`

用途：

- 构建 `module_annotation`
- 生成 `module_kegg_member`

### 2.9 Module 完整度矩阵

文件：

`row_data/kegg_module_completeness/completeness_matrix.tsv`

要求：

- 首列为 genome 标识
- 其余列为 module id，如 `M00001`
- 行必须能通过 `genome_name`、`genome_accession` 或 `leaf_label` 中的一种与当前包完全对齐

## 3. 构建流程

### 3.1 解析树

构建器先读 Newick，解析出：

- `parent`
- `children`
- `branch_length`
- 原始叶子节点列表

然后计算：

- `cumulative_branch_length`
- `node_in / node_out`

### 3.2 用 taxonomy 给树打 rank

对每个叶子，从 `gtdb_taxonomy` 解析出：

- domain
- phylum
- class
- order
- family
- genus
- species

再向上做共识传播，得到每个内部节点共享的 taxonomy 路径。树节点拓扑、节点数和枝长直接保留源 Newick，不为拆分 rank 插入虚拟节点；在同一原始节点首次出现的多个 rank 分别写入 `tree_named_taxon_index`，因此多个 rank 可以共享 `node_id`，同一个 `(rank, taxon_name)` 也允许在多个节点 occurrence 出现。

最终生成：

- `tree_node`
- `tree_named_taxon_index`
- `taxonomy`
- `tree_core.bin`

### 3.3 建立 genome 与叶子绑定

4.0 不再保留 `tree_leaf`。  
树叶与矩阵行的绑定职责直接移到 `genome`：

- `genome.leaf_node_id`：连接 species rank 叶子节点
- `genome.genome_id`：直接作为矩阵行号

规则：

- `genome_id` 必须是 `0-based`、连续、稳定、无空洞的 dense id
- 所有 annotation matrix 和 module completeness matrix 必须严格按 `genome_id ASC` 构建行顺序
- `leaf_label` 只允许作为构建期输入对齐键存在，不再进入运行期 schema

这一步会生成：

- `genome`
- `taxonomy`

其中运行期不再保留：

- `leaf_label`
- `leaf_order_index`
- `matrix_row_index`

### 3.4 蛋白与下载索引

读取所有 `.faa` 后，生成：

- `protein`

并保证：

- 同一 genome 的 `protein_key` 连续存放
- `genome.protein_key_start / protein_key_end_exclusive` 可以直接定位 genome 的蛋白区间
- `.faa` 始终由主进程顺序读取，`--workers` 不改变 FASTA 读取并发

### 3.5 注释字典与命中表

读取 `cog/kegg/pfam` 注释命中表和名字表后，生成：

- `cog_annotation`
- `pfam_annotation`
- `kegg_annotation`
- `protein_annotation`

规则：

- 运行期不再使用通用 `annotation`
- `protein_annotation.annotation_id` 指向对应类型的独立字典表
- `kegg_annotation` 会额外包含 module 成员中用到的 KO
- annotation 原始 TSV 不再强制整表一次性读入，而是按 `--annotation-chunk-rows` 分块处理
- 当 `--workers 1` 时，`cog / kegg / pfam` 文件顺序解析，并直接批量写入 `annotation_chunks/annotation_hits.sqlite`
- 当 `--workers > 1` 时，`cog / kegg / pfam` 文件分片并发解析，worker 先写入 Parquet chunk，再由主流程汇总到同一个 SQLite
- `annotation_hits.sqlite` 会按 `(annotation_type, annotation_value, genome_id, protein_key)` 去重
- 临时 annotation 层不再保存未使用的 `protein_id`
- 后续 `protein_annotation` 和 annotation matrix 都从这个临时 SQLite 继续生成，不再依赖一张常驻内存的大命中表
- 如果任一必需注释类型最终命中数为 0，构建会立即失败，不会继续写出缺少 COG/KEGG/PFAM 矩阵的运行期包
- 蛋白查找表超过 2000 万条时禁止 `--workers > 1`，避免多进程复制超大查找表
- 生成 `protein_annotation` 时会再落一层 `protein_annotation_chunks/*.parquet`，最后再写入运行期 SQLite

### 3.6 Module 表

读取 KEGG Module 原始文件后，生成：

- `module_annotation`
- `module_kegg_member`

当前 `module_kegg_member` 只保留：

- `module_annotation_id`
- `kegg_annotation_ids_json`

也就是“一个 module 对应一个有序 KO id 数组”。
这个顺序直接取代旧的 `member_order / step_index / step_logic / is_optional` 运行期存储需求。

### 3.7 热图矩阵

按 `genome_id ASC` 行顺序，把注释命中聚合成：

- `processed/matrices/cog.parquet`
- `processed/matrices/kegg.parquet`
- `processed/matrices/pfam.parquet`

特点：

- 行顺序固定
- 列名直接使用 annotation 值
- 不再写 `leaf_label` 辅助列

### 3.8 Module 完整度矩阵

把 `completeness_matrix.tsv` 对齐到 `genome_id ASC` 后，写成：

- `processed/module_completeness/module_completeness.parquet`

这份矩阵的路径信息不再单独存 `module_completeness_file`，而是并入 `matrix_file`。
运行期仍然保留 `processed/module_completeness/module_completeness.parquet` 文件本体，只是不再单独保留它的 registry 表。

### 3.9 写入 SQLite 和 manifest

最后写：

- `database/web_database.sqlite`
- `backend_ready/manifest.json`

manifest 只保留运行期入口信息，不再展开构建期 registry 内容。

## 4. project_data 中每个文件是怎么来的

### `database/web_database.sqlite`

来源：

- 树文件
- taxonomy 文件
- genome 叶子映射
- protein FASTA
- annotation TSV
- annotation names TSV
- module source
- module completeness TSV

### `processed/tree_core/tree_core.bin`

来源：

- 物种树 Newick
- taxonomy 共识路径

内容：

- 树骨架数组
- 命名 taxon 索引数组

### `processed/tree_core/{species_tree}.tre`

来源：

- 原始 Newick 原样复制

用途：

- 调试
- 审计
- 必要时回显原树

### `processed/matrices/*.parquet`

来源：

- protein FASTA
- annotation 命中表
- `genome.genome_id`

### `processed/module_completeness/module_completeness.parquet`

来源：

- `completeness_matrix.tsv`
- `genome.genome_id`

### `backend_ready/manifest.json`

来源：

- 构建结果汇总

## 5. 新增一棵树或一个数据库时怎么做

### 5.1 新增树

需要准备：

1. 新建 `row_data/GTDB_speciesTree/{new_tree_dir}/`
2. 放入唯一的 `*.tre` 树文件
3. 放入 `taxonomy.tsv`
4. 在 `speciesTree_genomesDatabase_mapping.txt` 里增加一行映射：`{new_tree_dir} : {genome_database_dir}`

### 5.2 新增 genome database

需要准备：

1. `row_data/protein_anno/{new_database}/protein/*.faa`
2. `row_data/protein_anno/{new_database}/annotation/*.tsv`
3. `row_data/protein_anno/{new_database}/genome_leafLabel_mapping.tsv`

然后让新树映射到这个 database。

### 5.3 重新构建

执行：

```powershell
python run_pipeline.py `
  --workspace F:\Project\web_database_deel `
  --output-root F:\Project\web_database_deel\project_data `
  --temp-root F:\Project\web_database_deel\temporary_file\build_stage `
  --workers 1 `
  --annotation-chunk-rows 250000 `
  --force
```

如果映射文件中只有一棵树，`project_data` 直接就是该包。  
如果有多棵树，`project_data` 下会生成多个独立子包。

## 6. 当前 4.0 构建的边界

当前版本已经明确做掉了这些事：

- `tree_leaf` 退出运行期 schema
- `is_cultured` 退出运行期 schema
- `taxon_representative` 直接下线
- `protein_sequence` 不再保留
- `module_completeness_file` 并入 `matrix_file`
- `genome_id` 与矩阵行号语义合并
- `module_kegg_member` 收敛为有序 KO id 数组
- `.faa` 由主进程顺序读取；annotation 在 `--workers > 1` 时支持分片并发
- annotation 大表支持 chunk 流式读取
- `--workers 1` 时 annotation 直接写入临时 SQLite；多进程时使用 staging Parquet chunk
- `protein_annotation` 仍先分块落盘，再写入最终 SQLite
- 最终 SQLite 使用构建期 PRAGMA、批量事务和延迟索引创建
- 注释字典表一次拆开，不再保留兼容层
- `project_data` 不再放旧版中间文件

当前仍保留一个过渡点：

- `taxonomy` 表仍然存在，用于下载 header；只是里面保存的是 rank 对应的命名 taxon `node_id`。这些节点由原树祖先锚点直接计算，不能再假设每个节点只保存一个 rank。

后续如果下载服务改成完全从祖先路径动态组装 taxonomy path，可以再把 `taxonomy` 彻底拿掉。
