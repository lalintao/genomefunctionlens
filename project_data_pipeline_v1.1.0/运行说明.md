# project_data 构建流程 1.1 运行说明

本文是 `project_data_pipeline_v1.1.0` 的运行时说明。命令中的 `<release_root>` 指本目录，`<workspace>` 指包含 `row_data/` 的工作区根目录。

## 1. 版本与范围

- 流水线版本：`1.1.0`
- 运行期 schema：`4.0`
- Python：`>= 3.11`
- 单元测试环境：Python 3.14.6、pandas 2.3.3、pyarrow 23.0.1、Biopython 1.88
- 完整库基准环境：Windows 10、Python 3.11.15、numpy 2.4.6、pandas 2.3.3、pyarrow 23.0.1、tqdm 4.70.1
- 本目录是构建代码冻结版，不包含原始数据或已生成的 `project_data`

### 1.1 本版本性能优化

- `--workers 1` 时 annotation 直接写入临时 SQLite，去掉 annotation Parquet 中继
- annotation 中间层移除未使用的 `protein_id` 字段
- 蛋白查找表改为单个整数打包 `genome_id + protein_key`，并避免单进程重复复制整表
- 最终 SQLite 使用构建期 PRAGMA、批量事务、延迟索引和近似 ANALYZE
- `manifest.json.build_performance.timing_seconds` 记录各阶段耗时

完整库基准：

```text
1.0 基线：约 1,071 秒（17 分 51 秒）
1.1 优化：约  844 秒（14 分 04 秒）
提速：约 21.2%
```

构建入口只有一个：

```bash
python run_pipeline.py build [options]
```

兼容旧调用方式：如果第一个参数以 `--` 开头，也会按 `build` 处理。

## 4. 构建前审计

先运行审计，再构建。推荐使用 `deep`：

```bash
python run_pipeline.py audit-row-data \
  --workspace <workspace> \
  --mode deep
```

返回码：

- `0`：没有 error，可以继续构建
- `1`：存在 error，不应继续构建

`fast` 模式检查目录、schema、树叶子对齐、genome 映射和 completeness 对齐；`deep` 模式还会实际解析 KEGG Module 源文件。

如果怀疑注释文件中的 `protein_id` 与 FASTA 不一致，可增加：

```bash
python run_pipeline.py audit-row-data \
  --workspace <workspace> \
  --mode deep \
  --scan-annotation-proteins
```

该选项会扫描全部 FASTA 和注释文件，明显更慢。

## 5. 执行构建

### 5.1 Linux / macOS

```bash
cd <release_root>
source .venv/bin/activate

python run_pipeline.py build \
  --workspace /path/to/workspace \
  --output-root /path/to/workspace/project_data \
  --temp-root /path/to/workspace/temporary_file/build_stage \
  --workers 1 \
  --annotation-chunk-rows 250000 \
  --force
```

### 5.2 Windows PowerShell

```powershell
cd <release_root>
.\.venv\Scripts\Activate.ps1

python run_pipeline.py build `
  --workspace F:\path\to\workspace `
  --output-root F:\path\to\workspace\project_data `
  --temp-root F:\path\to\workspace\temporary_file\build_stage `
  --workers 1 `
  --annotation-chunk-rows 250000 `
  --force
```

如果工作区结构符合默认约定，`--output-root` 和 `--temp-root` 可以省略：

```bash
python run_pipeline.py build --workspace /path/to/workspace --force
```

### 5.3 参数

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `--workspace` | 当前目录 | 工作区根目录 |
| `--output-root` | `<workspace>/project_data` | 产物根目录 |
| `--temp-root` | `<workspace>/temporary_file/build_stage` | 分块和暂存目录 |
| `--workers` | `1` | annotation TSV 解析进程数；1 为直写 SQLite，大于 1 为 Parquet 分片并发 |
| `--annotation-chunk-rows` | `250000` | annotation 流式读取 chunk 行数 |
| `--force` | 关闭 | 删除已有 output-root 后重建 |

内存提示：`--workers 1` 会把 annotation 直接写入临时 SQLite，是当前完整库的推荐模式。每个额外 worker 仍会复制一份蛋白查找表；只有确认内存足够时才提高到 `2` 或更高。`--workers` 不会让 FASTA 读取并行。

## 6. 输出结构

单树、单 genome database 时，`output-root` 本身就是运行期包：

```text
project_data/
  数据库4.0运行期数据库说明.md
  backend_ready/
    manifest.json
  database/
    web_database.sqlite
  processed/
    tree_core/
      tree_core.bin
      {tree_dir}.tre
    matrices/
      cog.parquet
      kegg.parquet
      pfam.parquet
    module_completeness/
      module_completeness.parquet
```

如果映射文件包含多棵树，`output-root` 下会为每棵树生成独立子包：

```text
project_data/
  {tree_dir_1}/
    backend_ready/
    database/
    processed/
    数据库4.0运行期数据库说明.md
  {tree_dir_2}/
    ...
```

每个子包都会带自己的 `manifest.json` 和运行期说明文档。`manifest.json` 中的 `pipeline_version` 应为 `1.1.0`，`schema_version` 应为 `4.0`。

## 7. 构建后验收

### 7.1 检查文件

```bash
test -f project_data/backend_ready/manifest.json
test -f project_data/database/web_database.sqlite
test -f project_data/processed/tree_core/tree_core.bin
test -f project_data/数据库4.0运行期数据库说明.md
```

### 7.2 检查 SQLite 与矩阵

在 `<release_root>` 下执行：

```bash
python - <<'PY'
import json
import sqlite3
from pathlib import Path
import pandas as pd

root = Path('/path/to/workspace/project_data')
manifest = json.loads((root / 'backend_ready/manifest.json').read_text(encoding='utf-8'))
print('pipeline_version =', manifest['pipeline_version'])
print('schema_version   =', manifest['schema_version'])

with sqlite3.connect(root / 'database/web_database.sqlite') as conn:
    print('integrity =', conn.execute('PRAGMA integrity_check').fetchone()[0])
    for table in ('genome', 'protein', 'protein_annotation', 'tree_node', 'matrix_file'):
        print(table, conn.execute(f'SELECT COUNT(*) FROM {table}').fetchone()[0])

for item in manifest['matrices']:
    frame = pd.read_parquet(root / item['matrix_path'])
    print(item['annotation_type'], frame.shape, 'expected', item['row_count'], item['column_count'])
    assert frame.shape == (item['row_count'], item['column_count'])
PY
```

验收要求：

- `PRAGMA integrity_check` 返回 `ok`
- 每个矩阵的实际 shape 与 manifest 中的 `row_count / column_count` 一致
- 所有矩阵行数都等于 `genome` 表行数
- manifest 的 `pipeline_version` 为 `1.1.0`

## 8. 安全与失败处理

- 构建会先完成输入发现和必需文件校验，再处理 `output-root`
- 输入校验失败时不会删除旧的产物
- `--force` 会删除已有 `output-root`；执行前必须确认路径正确
- 不带 `--force` 时，非空 `output-root` 会被拒绝
- `--force` 拒绝删除 workspace 根目录或其祖先目录
- 构建产物直接写入最终目录；如果构建中途因磁盘、内存或数据错误退出，可能留下不完整产物，需要修复原因后使用 `--force` 重跑
- SQLite 索引是在最终写库阶段创建并校验的；索引升级也可以单独执行：

```bash
python update_project_data_indexes.py --package-root /path/to/project_data
```

执行索引升级前应停止后端服务。该独立脚本默认不创建备份；生产环境请先自行备份 `web_database.sqlite`。

## 10. 已知边界

- 构建产物不是原子发布：中途失败可能留下部分目录
- `--workers > 1` 的内存占用会增加
- 蛋白查找表超过 2000 万条时，`--workers > 1` 会直接失败；必须使用 `--workers 1`
- 任一 COG/KEGG/PFAM 注释类型命中数为 0 时，构建会失败，不会发布缺少注释矩阵的包
- `update_project_data_indexes.py` 与 `runtime_indexes.py` 有部分索引逻辑重复，升级时需保持版本一致
- 运行期 `taxonomy` 表仍是下载 header 的过渡结构
- 1.1.0 已完成 20-genome smoke 和完整 10,122-genome 基准构建，输入审计为 0 error
